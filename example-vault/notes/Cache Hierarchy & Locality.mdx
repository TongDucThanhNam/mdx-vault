_Day 2 · Hardware Layer · Concept Note_

<h2 id="one-liner">One-liner [T]</h2>

**Cache mua latency bằng cách đánh cược vào locality** — CPU không nạp từng byte, nó nạp cả *cache line* (thường 64B) và cược rằng bạn sẽ dùng phần còn lại của line đó. Code thắng cược thì nhanh, thua cược thì chờ RAM.

<h2 id="mechanism">Mechanism [T]</h2>

<TraceBlock>{`Load địa chỉ X
  → L1 lookup (~1ns)         [HIT? trả về ngay — 90%+ trường hợp tốt]
  → L2 lookup (~4ns)         [miss L1 thì xuống đây]
  → L3 lookup (~40ns)        [shared giữa các core]
  → RAM fetch (~100ns)       [MISS toàn bộ — nạp NGUYÊN LINE 64B, không chỉ X]
  → Line fill vào L1/L2      [byte lân cận X giờ "miễn phí"]
  → Eviction                 [line cũ bị đẩy ra nhường chỗ]`}</TraceBlock>

/>

Hệ quả then chốt: truy cập `a[i]` lần đầu trả 100ns, nhưng `a[i+1..i+7]` (double 8B, line 64B) gần như miễn phí — **nếu bạn dùng chúng trước khi line bị evict**. Toàn bộ trò chơi locality nằm trong chữ "nếu" đó.

<h2 id="row-major">Row-major là gì — RAM không có 2 chiều [T]</h2>

**"Mảng 2 chiều" là ảo giác của ngôn ngữ lập trình — RAM là một dãy địa chỉ 1 chiều.** Khi bạn khai báo `a[4][4]`, compiler phải chọn một quy ước để ép phẳng nó xuống 1 chiều. Quy ước của C/C++/Rust/NumPy: **row-major** — xếp trọn hàng 0, rồi trọn hàng 1, cứ thế nối đuôi. Địa chỉ của `a[r][c]` = `base + (r*4 + c) × sizeof(elem)`.

| Code nhìn thấy: 2D | Cột 0 | Cột 1 | Cột 2 | Cột 3 |
| --- | --- | --- | --- | --- |
| Hàng 0 | a[0][0] | a[0][1] | a[0][2] | a[0][3] |
| Hàng 1 | a[1][0] | a[1][1] | a[1][2] | a[1][3] |
| Hàng 2 | a[2][0] | a[2][1] | a[2][2] | a[2][3] |
| Hàng 3 | a[3][0] | a[3][1] | a[3][2] | a[3][3] |

<FormulaLine>Code nhìn thấy: 2D → ép phẳng → RAM thật sự: 1D — hàng nọ nối đuôi hàng kia (màu = hàng gốc)</FormulaLine>

/>

**Row-major traversal** (`for r → for c`): đi đúng thứ tự RAM, mỗi bước +1 ô — phần tử kế tiếp gần như luôn nằm sẵn trong cache line vừa nạp. **Col-major traversal** (`for c → for r`): mỗi bước nhảy +4 ô trong RAM. Hai vòng lặp chỉ đảo thứ tự hai chữ `for`, nhưng về vật lý: một cái đi bộ dọc dãy nhà, cái kia nhảy cóc qua 4 nhà mỗi bước.

<HighlightBox title="[Version-dep]">
  Row-major là quy ước của C/C++/Rust/NumPy (mặc định). Fortran, MATLAB, R dùng **column-major** — cùng một code duyệt, số phận cache ngược hẳn nhau. Vậy mệnh đề đúng không phải "duyệt theo hàng thì nhanh" mà là: **duyệt theo đúng thứ tự bộ nhớ vật lý thì nhanh**.
</HighlightBox>

<h2 id="tradeoffs">Tradeoffs [T]</h2>

| Quyết định | Được gì | Trả giá gì |
| --- | --- | --- |
| Line lớn (64B thay vì 8B) | Spatial locality rẻ — 1 miss nạp 8 double | Truy cập rải rác lãng phí bandwidth; false sharing dễ xảy ra hơn |
| Cache nhỏ & gần (L1) | Latency ~1ns | Working set vượt 32–48KB → thrash xuống L2/L3 |
| Array-of-Structs | Code tự nhiên, 1 object liền khối | Duyệt 1 field của N object → nạp cả struct, dùng 1/8 line → SoA thắng cho analytics |

**Array-of-Structs — tính tổng field x: mỗi line nạp lên chỉ dùng được 1/3**

| Object 0 | Object 1 | Object 2 | Object 3 |
| --- | --- | --- | --- |
| x₀ · y₀ · z₀ | x₁ · y₁ · z₁ | x₂ · y₂ · z₂ | x₃ · y₃ · z₃ |

**Struct-of-Arrays — cùng phép tính: mỗi line nạp lên là 100% dữ liệu cần**

| Line x0–x3 | Line x4–x7 | Line x8–x11 |
| --- | --- | --- |
| x₀ · x₁ · x₂ · x₃ | x₄ · x₅ · x₆ · x₇ | x₈ · x₉ · x₁₀ · x₁₁ |

Cùng một logic với row vs col: **không phải cấu trúc dữ liệu nào "nhanh hơn" — mà là bố cục nào khớp với access pattern**. Duyệt cả struct → AoS thắng; duyệt một field xuyên N object (analytics, SIMD) → SoA thắng. Đây là lý do các columnar format (Parquet, DuckDB) tồn tại — cùng nguyên lý, scale lên disk page.

Quy luật rút ra được: hit ratio = `1 − stride/line_size` (khi stride ≤ line size). Stride = line size → **mỗi truy cập một line mới, hit ratio = 0**, dù bạn chỉ đọc 4 phần tử. Đây chính là câu self-test số 2 bên dưới, ở scale thật 64B.

<h2 id="failure-modes">Failure Modes [T]</h2>

| Failure | Cơ chế | Symptom production |
| --- | --- | --- |
| Cache thrash | Working set &gt; cache capacity → eviction liên tục | Throughput sụp khi data size vượt ngưỡng L2/L3 — đồ thị có "bậc thang" |
| Pointer chasing | Linked list/tree: node kế tiếp ở line ngẫu nhiên → không prefetch được | Array traversal nhanh hơn linked list 5–10× cùng N |
| False sharing | 2 core ghi 2 biến *khác nhau* nhưng cùng line → MESI invalidate qua lại | Thêm thread mà throughput không scale, thậm chí giảm, dù zero lock |

**Array — 8 phần tử liền kề = 2 line fill · địa chỉ kế tiếp đoán được trước → prefetcher nạp sẵn**

<FormulaLine>LINE 0: 0 · 1 · 2 · 3 | LINE 1: 4 · 5 · 6 · 7</FormulaLine>

**Linked list — cùng 8 node (n0→n7 theo thứ tự duyệt) rải khắp RAM = 8 line fill · địa chỉ node kế chỉ biết sau khi đọc node hiện tại → prefetcher mù**

| LINE 0 | LINE 1 | LINE 2 | LINE 3 |
| --- | --- | --- | --- |
| n0 · n4 | n2 · n6 | n5 · n3 | n1 · n7 |

Đọc thứ tự duyệt n0→n1→n2...: mỗi bước nhảy sang line khác line hiện tại → miss liên tục. Tệ hơn col-major một bậc: col-major nhảy *đều đặn* nên hardware prefetcher còn học được stride; pointer chasing là **dependent load** — không đọc xong node này thì không biết địa chỉ node sau, prefetch bất khả về nguyên tắc. Đây là lý do array thắng linked list 5–10× dù cùng Big-O.

<HighlightBox title="Chú ý">
  False sharing *không có widget* — có chủ đích. Simulation tự code sẽ output con số mình lập trình sẵn = zero evidence value. Mechanism này cần **benchmark thật + perf stat** → xem Evidence Log. Prerequisite còn thiếu: MESI coherence (chưa học, maturity L1).
</HighlightBox>

<h2 id="self-test">Self-test [Q]</h2>

Trả lời từ trí nhớ *trước* khi bấm reveal. Sai → quay lại đúng section được link, không đọc lại cả note.

<SelfTest>
  <SelfTestItem level={3} question="Mảng 4×4, line = 4 phần tử: vì sao col-major miss cả 16 lần trong khi mỗi line chứa sẵn 4 phần tử liên tiếp?">
    Col-major truy cập theo stride 4 = đúng bằng line size → phần tử kế tiếp *luôn* nằm ở line khác. Cache 1-line phải evict line vừa nạp khi mới dùng 1/4 nó. Đến khi vòng lặp quay lại cột sau, line cũ đã bị đẩy ra từ lâu → mọi truy cập đều là cold miss. (→ [Widget 01](#widget-row-col))
  </SelfTestItem>

  <SelfTestItem level={4} question="Line 64B, mảng double 8B. Stride bao nhiêu phần tử thì spatial locality biến mất hoàn toàn — và hit ratio thay đổi thế nào ở stride 2, 4, 8?">
    Line chứa 64/8 = **8 double**. Stride 2 → dùng 4/8 line → hit 50%. Stride 4 → 25%. **Stride 8 → mỗi truy cập một line mới → hit 0%**, locality chết hẳn dù pattern hoàn toàn "có quy luật". Công thức: hit = 1 − stride/8 (stride ≤ 8). (→ [Widget 02](#widget-stride))
  </SelfTestItem>

  <SelfTestItem level={5} question="Trong PostgreSQL, hiện tượng nào ở tầng buffer pool đóng vai trò tương đương 'duyệt col-major'?">
    `[PG-specific]` Index scan trên cột có **correlation thấp** với thứ tự vật lý của heap: mỗi TID trỏ tới một heap page khác nhau → mỗi row fetch là một page read riêng, giống mỗi phần tử một cache line. Cùng số row, index scan correlation thấp có thể thua seq scan — lý do planner đôi khi "từ chối" dùng index. Cache line ↔ heap page, L1 ↔ shared_buffers, RAM fetch ↔ disk I/O. (→ [[bridge-locality-cpu-cache-to-buffer-pool]], học kỹ Day 10–11)
  </SelfTestItem>
</SelfTest>
